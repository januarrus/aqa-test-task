# Автотесты для тестового задания AQA Engineer

Автотесты для веб-сервиса с одним эндпоинтом `POST /endpoint` (действия `LOGIN`, `ACTION`, `LOGOUT`).
Внешний сервис (`/auth`, `/doAction`) подменяется заглушкой WireMock, поэтому тесты сами управляют его ответами
и проверяют, какие запросы туда отправило приложение.

**Стек:** Java 17, JUnit 5, WireMock, RestAssured, AssertJ, Allure, Maven.

## Что проверяется

| Раздел | Проверки |
|---|---|
| Доступ по API-ключу | запрос без ключа и с неверным ключом отклоняется, во внешний сервис ничего не уходит |
| Формат токена | неверная длина, строчные буквы, спецсимволы, пробел, кириллица, пустой и отсутствующий токен; все варианты корректного по документации токена (цифры, A–F, G–Z, весь алфавит) |
| Параметр action | неизвестное значение, другой регистр, лишние пробелы, пустое и отсутствующее значение |
| Вход (LOGIN) | успешный вход при ответах 200/201/204; отказ при ответах 4xx/5xx и 3xx, при таймауте и обрыве соединения, токен при этом не сохраняется; повторный вход; корректность запроса в `/auth` (метод, заголовки, тело) |
| Действие (ACTION) | успешное действие после входа; запрет без входа; ошибки внешнего сервиса; сессия сохраняется после ошибки; вход одного пользователя не даёт прав другому |
| Выход (LOGOUT) | после выхода действие недоступно; выход без входа; повторный вход после выхода; выход одного пользователя не затрагивает другого |

Красные тесты в отчёте — это найденные дефекты приложения, они описаны ниже.

## Как запустить

Нужны JDK 17 или 21 и Maven 3.9+.

1. Положите `internal-0.0.1-SNAPSHOT.jar` в папку `app/` в корне проекта.
2. Запустите тесты (приложение и заглушка стартуют автоматически):

   ```
   mvn clean test
   ```

3. Откройте отчёт:

   ```
   mvn allure:serve
   ```

Если приложение уже запущено вручную, добавьте `-Dapp.start=false`.
Другой путь к jar: `-Dapp.jar=путь/к/файлу.jar`. Лог приложения во время прогона пишется в `target/app.log`.
Порты 8080 и 8888 должны быть свободны.

## Как читать отчёт

Тесты сгруппированы по разделам (вкладка «Функциональность» / Behaviors). Каждый тест состоит из шагов на русском языке.
К шагам приложены запрос к приложению, его ответ и список запросов, которые получил внешний сервис.

## Найденные дефекты

### BUG-1. Токены с буквами G–Z отклоняются (критический)

**Шаги:** отправить `LOGIN` с токеном `GHIJKLMNOPQRSTUVWXYZ012345678901` (32 символа, только A-Z и 0-9).
**Ожидается:** токен принят, приложение обращается к `/auth`.
**Фактически:** HTTP 400, `token: must match "^[0-9A-F]{32}$"` — приложение принимает только буквы A–F,
то есть большинство корректных по документации токенов не может войти.
**Тесты:** «Токен, корректный по документации, принимается» (варианты с буквами G–Z).

### BUG-2. Ответ 3xx от внешнего сервиса считается успешным входом (критический)

**Шаги:** внешний сервис отвечает на `/auth` кодом 301 или 302; отправить `LOGIN`.
**Ожидается:** вход не выполнен — перенаправление не подтверждает токен.
**Фактически:** `{"result":"OK"}`, токен сохраняется, после этого `ACTION` выполняется.
**Тесты:** «Вход не выполнен, если внешний сервис ответил перенаправлением».

### BUG-3. При сбое внешнего сервиса причина ошибки не сообщается (средний)

**Шаги:** внешний сервис отвечает на `/auth` или `/doAction` кодом 4xx/5xx, не отвечает дольше 10 с или недоступен.
**Ожидается:** понятная причина в поле `message` (документация обещает `"message": "reason"`).
**Фактически:** HTTP 500 и `"message": "Internal Server Error"` во всех случаях — по ответу нельзя понять,
отказал ли внешний сервис в доступе, упал или не ответил.

### BUG-4. В action принимаются значения с лишними пробелами (низкий)

**Шаги:** отправить `action=" LOGIN"` или `action="LOGIN "`.
**Ожидается:** ошибка — по документации допустимы ровно три значения.
**Фактически:** пробелы молча обрезаются, вход выполняется.
**Тесты:** «Действие с лишними пробелами отклоняется».

### BUG-5. Некорректные HTTP-коды на неподдерживаемые запросы (низкий)

Проверено вручную:
- `GET /endpoint` → HTTP 500 вместо 405 Method Not Allowed;
- тело в формате JSON вместо формы → HTTP 500 вместо 415 Unsupported Media Type;
- заголовок `Accept: text/html` → HTTP 406 с HTML-страницей вместо JSON;
- пустой `action` → причина `invalid action 'null'` вместо пустого значения.

## Поведение, не описанное в документации

Зафиксировано тестами как фактическое поведение:
- повторный `LOGIN` уже вошедшего токена → HTTP 409 `Token '...' already exists`, внешний сервис не вызывается;
- `ACTION` и `LOGOUT` для неизвестного токена → HTTP 403 `Token '...' not found`;
- ошибка неверного API-ключа → HTTP 401 `Missing or invalid API Key`;
- ответ внешнего сервиса ждётся около 10 секунд.

Проверено вручную: 10 одновременных `LOGIN` с одним токеном дают ровно один успешный ответ и один запрос в `/auth`.
